## Concerns

### 1. `Features/SmartScan/Views/*.swift` were missing from the pbxproj
This is the most important finding of the task. The Phase A `ScanResultsView`,
`ScanResultsViewModel`, and `ScanTreeRow` source files exist on disk
(`kWise/Features/SmartScan/Views/`) and were introduced in A8 / A10 /
A11, but the `generate_project.py` `swift_files` list never registered
`Features/SmartScan/Views/*.swift` (only the root `Features/SmartScan/*.swift`
and `Features/SmartScan/Models/*.swift` were listed). The result:

- The main app **built** without these files because nothing else depended on
  them at compile time (they're leaf views).
- The kSpaceClean swiftmodule did not contain `ScanResultsView`,
  `ScanResultsViewModel`, or `ScanTreeRow` symbols.
- A previous test that tried to reference `ScanResultsViewModel` (via
  `@testable import kSpaceClean`) would have failed with "cannot find in scope".

The A13 task surfaced this gap: `ScanResultsViewSnapshotTests.swift` would
not compile until the three missing files were registered. I added them to
`generate_project.py` and regenerated the pbxproj; this is the single line
of work that unblocked the snapshot tests.

**Implication for prior tasks.** Tasks A8 / A10 / A11 / A12 all created files
in `Features/SmartScan/Views/` (and possibly other subfolders) but didn't
verify the generator registered them. The Phase A components were effectively
"dead code" — not compiled, not exercisable by any test. After this A13 fix,
they are now part of the main binary's swiftmodule and visible to
`@testable import`. A future A14 (Phase A Polish + Buffer) should:

- Audit the generator's `swift_files` list against every `.swift` file on
  disk and add any missing entries.
- Add a CI guard: `find kSpaceClean -name "*.swift" | sort` vs the
  generator's list, fail if they diverge.

### 2. Snapshot tests are structural, not pixel-based
Per the task description and the A6 finding, the project has no
image-snapshotting library and the macOS 13 SDK lacks `ImageRenderer`.
`SnapshotTestCase` therefore asserts only that the view hosts without
crashing and produces a non-zero frame at the target canvas size. This is
weaker than true pixel snapshots, but matches the project's current tooling
budget. A future task could adopt `swift-snapshot-testing` for pixel
coverage; the helper is the single point of change.

### 3. `ScanResultsViewSnapshotTests.swift` lives at `Tests/` not `Features/SmartScan/Tests/`
The brief specified the file path as
`kWise/Features/SmartScan/Tests/ScanResultsViewSnapshotTests.swift`,
but the existing test convention keeps every test under the flat
`kWise/Tests/` directory (see `generate_project.py` `test_files`
list). I placed the file under `Tests/` to match the convention; the brief's
suggested path would have required introducing a nested-test-files code path
in the generator (which I attempted first, then reverted when the nested
location failed to expose the SmartScan types — see Concern §1 root cause).

### 5. `SnapshotTestCase` is `@MainActor`
`NSHostingView(rootView:)` is main-actor isolated under
`SWIFT_STRICT_CONCURRENCY = complete`. The base class therefore must be
`@MainActor`, which in turn forces every subclass to be `@MainActor`
(matching the existing convention in `RiskBadgeTests`, etc.). This is the
correct behaviour for macOS UI tests but worth noting for future test
authors who copy/paste the base.

### 6. Brief specified only 1 test class per file, I added multiple
The brief's `RiskBadgeSnapshotTests.swift` had one test class; the same
file in this commit has one test class (`RiskBadgeSnapshotTests`) plus four
sibling test classes in the same file (covering IndeterminateCheckbox,
SkeletonRow, EmptyStateScreen, ToolbarView). The brief did not name files
for these four components; I co-located them in
`PhaseAComponentSnapshotTests.swift` to keep the helper file count down and
to match the spirit of "structural tests for all Phase A components"
called out in the task description.
